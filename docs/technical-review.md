# Babylon.js RTS 技术评审

日期：2026-10-20｜结论：方案可进入逻辑原型阶段；群体移动与动态阻挡需先做技术验证。

## 1. 评审依据与限制

工作目录当前没有应用源码、依赖清单和可运行测试。本评审是设计评审，不代表实现已通过测试，也不提供未经测量的性能结论。

Babylon.js 用于场景、相机、拾取和表现；RTS 的经济、订单、寻路、战斗和AI由应用实现。主要成本在规则与多单位交互，简化粒子只能降低表现层成本。

## 2. 技术栈与取舍

| 项目 | 建议 | 原因与代价 |
| --- | --- | --- |
| 开发 | TypeScript严格模式、Vite | 便于数据建模、模块开发与静态构建 |
| 渲染 | Babylon.js `@babylonjs/core`，首版WebGL2 | 不将WebGPU设为运行前提；无WebGL2时显示明确提示 |
| UI | HTML/CSS覆盖画布 | 资源条、菜单和队列容易调试；需处理输入穿透 |
| 模型 | 几何体、共享材质 | 无美术依赖，后续可接glTF；届时再引入loaders |
| 模拟 | 纯TypeScript、固定步长、独立于Scene | 支持无渲染测试；需要明确状态和事件边界 |
| 寻路 | 占用网格+A*+局部避让 | 适合平面地图、动态建筑；群体拥挤需要专门处理 |
| 物理 | 首版不引入刚体引擎 | 碰撞与攻击按逻辑圆/矩形计算，避免两套位置权威 |
| 测试 | Vitest逻辑测试、Playwright关键流程 | 验证经济与规则不变量，加少量浏览器验收 |
| 服务端 | 首版无 | 静态资源即可运行；联机需要后续独立设计 |

实施时核对所选稳定版本的兼容性并提交锁文件，Babylon相关包保持同版本。不在未安装验证前写死“最新版”版本号。

## 3. 模块与依赖

```text
键鼠输入 ─→ InputController ─→ CommandQueue ←─ AIController
                                  ↓
                         Simulation（权威状态）
                         ├─ Economy / Build / Production
                         ├─ Navigation / Movement
                         ├─ Targeting / Combat / Death
                         └─ Victory / DomainEvents
                                  ↓ 只读状态、事件
                       BabylonRenderer + HTML HUD
```

建议目录：

```text
src/
  app/          启动、暂停、重开、资源释放
  simulation/   世界、实体、命令、系统、固定时钟
  navigation/   网格、A*、阻挡版本、寻路调度
  ai/           通过公共命令接口决策
  rendering/    Babylon场景、相机、实体视图、特效
  input/        选择、编队、命令模式
  ui/           HUD和菜单
  config/       单位、建筑、地图数据
tests/
  simulation/
  scenarios/
  e2e/
```

模拟层禁止依赖Babylon对象、DOM、真实时间和全局随机数。以普通数值保存XZ坐标。首版采用实体ID与组件数据表，不引入完整ECS框架；组件包含归属、位置、生命、移动、战斗、采集、建造和生产。

渲染侧持有 `EntityId → View` 映射。Mesh销毁不能触发逻辑死亡；表现帧的动画事件不能扣血。所有数值由配置加载并校验。

## 4. 模拟时钟与命令

- 固定步长50ms，使用累积时间推进；每渲染帧最多补5步，超额时间丢弃并记录过载，避免卡顿后长时间追赶。
- 过载时游戏时间可能落后真实时间，首版接受此降速策略。后台直接暂停并清空累积时间。
- 渲染按上/当前模拟位置插值；低FPS时移动更粗糙但规则不以帧数计时。
- 命令包含 `sequence、playerId、entityIds、type、payload`，在步边界按序处理并重新验证归属、存活、余额、人口和目标。
- 单步顺序固定：命令 → AI生成下一步命令 → 经济/施工/生产 → 寻路/移动 → 目标与攻击意图 → 伤害批量结算/死亡清理 → 胜负 → 事件发布。
- 同步命中只结算一次；当前步合法存活攻击者可互杀。新出生单位从下一步开始行动。
- 暂停、结束后拒绝世界变更命令；重开清空命令队列、选择与AI状态。

采用固定随机种子、稳定ID遍历、命令日志和状态摘要，便于同一运行环境复现。固定步长不等于跨浏览器确定性；首版不承诺锁步联机或跨版本回放。

## 5. 寻路评审

### 选择网格A*的理由

Babylon官方提供导航网格和Crowd方案，当前文档还提供TileCache动态局部更新能力。不能简单认为导航网格无法处理动态障碍。[官方导航网格文档](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/crowdNavigation/createNavMesh.md)、[TileCache文档](https://doc.babylonjs.com/features/featuresDeepDive/crowdNavigation/v2Intro/v2WhatsNew/v2TileCache/)。

本项目平面地图、格点建筑、规模较小，选择自有网格的工程判断是让“建筑可放置”和“单位可通行”共用规则，便于测试。代价是局部避让和拥堵恢复需自己实现。未来复杂坡地再评估Recast/Crowd；若原型证明自研移动无法达标，应在扩展经济玩法前更换方案。

### 实施约束

- 128×128网格；八方向搜索，禁止对角切角，启发式使用八方向距离。
- 单位半径初始统一0.35；阻挡计算须考虑半径，不能只判断中心点。路径平滑使用相同的扫掠碰撞规则。
- 地形/资源/建筑硬阻挡独立于单位占用；不因单位每步移动而使所有全局路径失效。
- 放置/销毁建筑、耗尽资源时更新阻挡版本；移动前检查下一段是否仍可行，失效路径进入重寻路队列。
- 建筑放置检查占地无单位、施工位置可达，并用连通性校验保留预设主通道锚点之间的连接。
- 群体分配附近不同终点；终点生成按稳定顺序，避免反复交换目标。
- 单位使用空间哈希查询附近邻居，做局部分离、优先权与等待；每次位移再检查硬障碍，分离力不可把单位推入建筑。
- 窄路通过稳定ID优先权让行；持续2秒无有效进展则重新规划，连续3次失败进入阻塞待机并通知玩家，允许重新下令。
- 寻路采用可跨步恢复的队列，每模拟步总扩展预算2,000节点；每单位重算间隔至少0.5秒。预算是初值，按压力测试调整。
- 不可达搜索需有节点上限和明确失败结果，不能每帧重复完整搜索。

优先验证20/50/100单位经过窄口、迎面对行、移动中新增建筑、目标被围住。若100单位下明显长期卡死，不能以特效优化替代移动修复。

## 6. 规则一致性与生命周期

资源和人口由统一事务入口修改，禁止UI或AI直接增减。训练入队、取消、出生、建筑销毁分别使用独立原子操作，并维护以下不变量：

- 金币、木材、资源点储量、携带量均非负。
- 已用人口等于存活单位人口总和，预留人口等于所有队列订单总和。
- 每个订单只能处于排队、训练、等待出生、已完成、已取消之一。
- 每个实体最多发生一次死亡事件，死亡清理释放交互位、占地、选择和目标引用。
- 目标消失时通过ID有效性检查结束当前动作，不持有失效对象。

采集状态采用“前往资源 → 采集 → 前往主基地 → 交还”；施工、攻击、移动也采用显式状态。新命令负责清理旧状态的预约和目标，防止工人离开后仍占采集位。

重开统一释放Scene、输入监听、UI订阅、粒子池和实体视图，再创建新世界。时钟由单一主循环管理，不为每单位设置定时器。

## 7. 表现与性能

Babylon的标准ParticleSystem提供容量和生命周期控制，足以实现首版短促命中效果；无需节点粒子编辑器或复杂GPU特效。[官方ParticleSystem介绍](https://doc.babylonjs.com/features/featuresDeepDive/particles/particle_system/particle_system_intro)。

- 共享几何体与材质；先用普通Mesh保证拾取和实体映射清晰，出现实测瓶颈再评估实例化。
- 单一主光源，默认不启用实时阴影、后处理和复杂PBR。
- 特效对象池、总粒子上限200；关闭表现不得改变模拟状态摘要。
- HUD资源字段按变更更新；选中血条最多10Hz更新。调试面板显示单位数、寻路队列长度、模拟耗时、帧耗时。
- 静态装饰不加入逻辑碰撞，地形占用来源必须唯一。

## 8. 风险与评审门槛

| 风险 | 严重度 | 缓解与通过条件 |
| --- | --- | --- |
| 群体堵塞、互相推挤 | 高 | 先做移动验证；正常可达场景到达、不可达场景有限时间报告 |
| 动态建筑导致穿墙或路径失效 | 高 | 共用阻挡数据；放置后立即阻挡、毁坏后恢复通行 |
| 资源/人口重复扣返 | 高 | 原子操作、死亡清理与不变量测试 |
| AI无法完成经济循环 | 中 | AI走公共命令；固定种子连续模拟记录失败原因 |
| 游戏范围膨胀 | 高 | 英雄/迷雾/联机不进入首版完成门槛 |
| 浏览器性能未知 | 中 | 目标设备实测；预算失败后决定优化，不宣称已达标 |
| 原作素材依赖 | 中 | 使用原创命名、几何资产与自制UI |

评审建议：先通过移动与动态阻挡门槛，再实现经济闭环；之后接入战斗和AI。完成首版验收后再讨论英雄与表现升级。当前没有代码级阻断问题可判定，运行质量仍待实现验证。
